# 三层规则（must / should / can）

## 0 治理（先于一切）

| 字段 | 值 |
|---|---|
| 规则版本 | 1.2.0 |
| 批准日期 | 2026-11-21 |
| 最后修订 | 2026-11-21 |
| 效力 | 本规则优先于其它实践；相互冲突时以本文件为准 |
| 冲突裁决 | 安全与只读边界 > must > 项目约定 > should > can |
| 修订条件 | 理由 + 批准人 + 迁移计划，缺一不得落盘；改完同步 `templates/AGENTS.md` 与各宿主入口 |

> 为什么要有这一段：门禁能判「这次改动有没有违反规则」，判不了「规则本身被绕过没有」。
> 规则文件自己不带版本与批准日期，就没人说得清「现在执行的是哪一版」。

## 1. 分层语义

| 层 | 语义 | 违反后果 |
|---|---|---|
| must | 必须执行，无例外 | 门禁直接 `FAIL`，不得进入下一阶段 |
| should | 默认遵守 | 可例外，但必须记录原因、影响与补偿 |
| can | 按需选用 | 不选不记录 |

判定顺序：先查 must，再查 should 是否已声明例外，最后才看 can。

## 2. must（19 条）

1. 每条需求写成「当…发生时，系统应…」，并至少对应一个验收点。
2. 验收点必须可判定（能给出通过/不通过），不得写成「体验更好」。
3. 需求未经人确认，不得进入方案设计；方案未经人确认，不得进入开发。
4. 开发、测试、审查必须是三个独立上下文，测试与审查不得读取开发过程自述。
5. 审查只看实际改动（diff / 文件内容），不看开发者结论。
6. 门禁只允许三态：`PASS`、`FAIL`、`BLOCKED`，不得用「基本完成」代替。
7. 未验证项必须写明：未验证原因、影响范围、补验条件。
8. 数据边界只读：只读本地代码、文件与用户提供的日志；不连接数据库、缓存、远程服务。
9. 密钥、令牌、个人数据不得写入需求包、日志片段或提交信息。
10. 关键动作与验证结果必须回写 `state.md`，证据写路径而非口头结论。
11. 阻塞发生时立即记入 `state.md`，写清「卡在哪、等什么、谁能解」。
12. 发布与回退材料未齐，不得进入验收。
13. 执行 harness 必须显式调用技能入口，并在 `state.md` 记录调用来源（技能名、时间、执行者）。
14. 建仓、推送、发布等外部不可逆动作前，必须确认「项目名、目标仓库名、可见性」三项，写入 `state.md` 后才可执行；确认缺失即 `BLOCKED`。
15. UI 需求必须有冻结参考（路径 + sha1）与可重放采集命令；没有视觉证据不得进审查，`computer-use` 不得用于回归与多轮比对。
16. 动手前（改代码、改文档、发布前）必须先跑 `node harness/scripts/selfcheck.mjs`；退出码非 0 表示有阻断项，先修再动，不得带着阻断项开工。
17. 用户只提出需求时，非只读需求**自动进入需求包流程**，不等用户额外输入 `/harness` 或 `ai-workflow` 触发词；已读 `AGENTS.md` 的项目默认处于工作流内。
18. 命中某个技能后，**先读它的 SKILL.md 正文再动手**：跑 `node harness/engine/harness.mjs skill <名字>` 拿「读这个文件」的路径，读完才动手。**未读不得输出该技能的内容，也不得凭记忆复述它**。正文超长的，按该技能自己的「按需再读」表只读需要的分册，不整包吞。
19. 功能类需求（有界面、流程、入口或交互）开工前必须：① 跑 `node harness/engine/harness.mjs domain <关键词>` 查域规则；② 在需求包里写满**功能设计卡**六问（用户旅程位置 / 行业基线 / 我们的现状与差距 / 决策点与后果 / 不做什么 / 交付形态）。域规则未收录时，必须先做同行对标，并把带证据锚的行业基线沉淀到 `harness/domains/<域>.md`。缺任一项 G1 FAIL。

## 3. should（12 条）

1. 一次只加载当前阶段需要的上下文，不预读后续阶段材料。
2. 小改动按实际影响简化流程（见 `gates.md` §7），但 must 不豁免。
3. 需求包文档增量更新，不覆盖历史结论；被推翻的结论标「已废弃」并写原因。
4. 长期 memory 只收「已验证 + 可复用」的经验，单次结论不进长期记忆。自动写入只进候选池；正式记忆须满足三条件（复现 ≥3 ∧ 作用域 ≥2 ∧ 满 30 天）并经人确认。
5. 日志先聚合再抽关键片段，片段不超过必要长度。
6. 同一问题连续两次修复失败，停下来写假设清单，不再盲改。
7. 涉及权限、删除、发布、资金的动作，先给影响面再执行。
8. 跨模块改动先列出受影响文件与调用方，再动手。
9. 交付前跑一次自检：must 逐条对照，缺失项补记录。
10. 换人/换 agent 续接时，先读 `state.md` 再核对代码，不凭记忆。
11. 门禁通过后写进候选池的是「事件」，需人工提炼成可复用经验后另写一条（类别不用「事件」），否则永远聚合不起来。
12. 行业基线必须写「同行做到了什么」而不是「竞品叫什么名字」，且每条带证据锚（可公开引用的 URL 带章节，或 `文件:行号`）；拿不到证据锚的条目不进域文件，只在功能设计卡里标「待核实」。

## 4. can（按需）

- 竞品或同类实现对标；
- 原型验证；
- 性能压测与容量评估；
- 可观测性增强（指标、追踪）；
- 文档图示化。

## 5. 例外协议（should 专用）

例外必须同时写清四项：

```text
规则：<哪一条 should>
原因：<为什么这次不做>
影响：<可能造成什么>
补偿：<后续怎么补，何时补>
```

四项缺一，视为 must 违规。

## 6. 冲突裁决

优先级：**安全与只读边界 > must > 项目约定 > should > can**。

当项目约定与 must 冲突时：停下，记录冲突点，交人裁决；不得自行放宽 must。

## 7. 违规处理

| 场景 | 处理 |
|---|---|
| must 违规 | 门禁 `FAIL`，回到违规阶段重做 |
| should 未声明例外 | 按 must 违规处理 |
| 证据缺失 | 该项记为未验证，门禁最多 `BLOCKED` |
| 无法判定 | `BLOCKED`，写清缺什么才能判定 |
20. **开工第一件事是跑 `node harness/engine/harness.mjs begin "<一句话需求>"`，不跑就动手算违规。** 它一次给出档位、红灯、可用工具与**相关经验（BRIEF）**——经验只从这里出来，不跑它等于每次都在失忆。BRIEF 有内容就必须用：说清这次怎么用上，或说清为什么不适用。**它给的「技能」行不是建议而是下一步**：先跑 `skill <第一个>` 读正文再动手；没命中就自己按需求判断该读哪个，不能因为没建议就跳过。红灯没清不动手。
