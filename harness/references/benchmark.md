# 需求分析 · 同行对标

> 定位：把「用户说的一句话」拆成可判定的需求条目，并逐条找到同类 / 同行的真实做法，作为方案取舍的依据。
> 这一环是 G1 的组成部分：没有对标证据的需求，不允许进入方案设计。

## 1. 什么时候必须做

- 所有非 S 档需求（S 档至少做 1 条对标，写明「同类最简做法」）。
- 需求里出现「更好用、更快、更智能、像 XX 那样」等主观词时，强制做。
- 涉及交互流程、默认值、失败提示、权限可见性时，强制做。

不适用：纯内部重构、纯依赖升级、纯文案修正。不适用也要在 `00-requirement.md` 写一句理由。

## 2. 五步法

### 第 1 步：拆成需求条目

- 一句话需求 → `R-01`、`R-02`……每个条目写成「当 <触发条件> 时，系统应 <可观测行为>，以便 <目的>」。
- 每个条目配至少一个 `AC-xx`，可被测试或人工复现判定。
- 拆不出来说明需求本身还模糊，先拷问，不要硬拆。

### 第 2 步：先定覆盖维度，再为每个取值找对标

**声明先于对标**：先问清这次到底要覆盖哪些维度、每个维度有哪些取值，写进
`覆盖维度：端=Web,iOS; 角色=管理员,普通用户`。端只是其中一种，别只盯端。

反问时按候选维度过一遍（命中就展开，不适用就写理由）：端、角色/权限、状态（默认/空/加载/错误/无权限）、语言/地区、时区、环境（开发/预发/生产）、数据规模、支付渠道、设备能力、浏览器/系统版本、可访问性、离线/弱网、账号类型、租户、币种/税率。

- 每个维度至少 2 个取值时，**每个取值都要有自己的对标基线**：该取值真实存在的规范（iOS HIG / Material / 小程序设计指南）或同类产品在该取值下的实现；
- 取值之间的差异（导航、手势、权限、字体、支付、分享、文案长度）本身就是要对标的事实，不要用「都一样」糊过去；
- 单取值需求：至少 2 个不同来源（同类产品 + 同行实现）；
- 来源必须可追溯：URL、公开文档、开源仓库文件、可复现截图。**只写产品名不算证据。**

### 第 3 步：采集可观测事实

只记录能观察到的行为，不写推测：

| 维度 | 要采集什么 |
|---|---|
| 入口 | 从哪进、几步到达、是否需要登录 |
| 主路径 | 操作顺序、每步反馈、默认值 |
| 边界 | 空数据、重复提交、无权限、超时、离线 |
| 失败处理 | 报错文案、可恢复性、是否保留用户输入 |
| 数据与精度 | 数据来源、刷新频率、精度与单位 |
| 权限与可见性 | 谁能看、谁能改、审计留痕 |
| 留存与隐私 | 存多久、能否导出/删除、是否二次使用 |
| 性能体感 | 首屏、批量操作、长列表行为 |

### 第 4 步：得出取舍

每条需求给一个明确结论，四选一：

- **采纳**：对标做法已是最优，照做并写明抄的是哪一条。
- **改造**：方向对但需适配本地约束，写清改什么、为什么。
- **不采纳**：明确拒绝，写清代价（用户会失去什么）与补偿方案。
- **差异化**：刻意不同，写清差异化带来的收益与验证方式。

「都行」「看情况」「业界通用」不算结论。

### 第 5 步：落盘

写进 `00-requirement.md` 的「需求分析与同行对标」表，一行一条需求：

```text
| 需求 | 对标对象 | 来源 | 他们的做法 | 我们的取舍 | 理由 |
```

G1 机判规则（引擎执行）：

1. 正文里出现的每个 `R-xx` 都要有对应行；
2. 来源列必须是 URL 或本地证据文件（`.md/.pdf/.png/.jpg/.txt/.html`）；
3. 取舍列不能是占位符；
4. 全表至少 2 个不同来源。

任一不满足 → G1 `FAIL`。

## 3. 证据等级（用于判断可信度）

| 等级 | 证据 | 可否支撑决策 |
|---|---|---|
| A | 亲手复现的操作路径 + 截图 / 录屏 | 可以 |
| B | 官方文档、帮助中心、API 文档 | 可以 |
| C | 开源仓库代码或测试用例 | 可以，需注明版本/commit |
| D | 第三方测评、文章、视频 | 仅作线索，需回到 A/B/C 核实 |
| E | 模型记忆、印象、猜测 | 禁止作为证据 |

拿不到 A/B/C 时，结论只能是 `BLOCKED`，并把缺什么、找谁、何时补写进 `state.md`。

## 4. 反模式

- 只写「参考了竞品」不写具体行为 → 无效对标。
- 把「行业惯例」当来源 → 无效。
- 一条需求对标 5 个产品但没结论 → 信息过载，不算完成。
- 用对标结果反推需求（对标有就抄） → 需求被工具绑架，必须先过澄清清单。
- 对标结论与 `01-design.md` 方案不一致 → 以对标表为准，回头改方案或改结论。

## 5. 与其它环节的衔接

- 澄清清单六类问题，优先用对标事实回答；答不上来的才去问人。
- `01-design.md` 的取舍必须能追溯到对标表的某一行。
- 审查阶段核对：方案里出现的「业界做法」是否都能在对标表里找到来源。
- 对标结论若被后续验证推翻，写进 `harness/memory/long-term.md`，注明证据与复审时间。
