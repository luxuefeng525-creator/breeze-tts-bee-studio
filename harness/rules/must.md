## 2. must（19 条）

1. 每条需求写成「当…发生时，系统应…」，并至少对应一个验收点。
2. 验收点必须可判定（能给出通过/不通过），不得写成「体验更好」。
3. 需求未经人确认，不得进入方案设计；方案未经人确认，不得进入开发。
4. 开发、测试、审查必须是三个独立上下文，测试与审查不得读取开发过程自述。
5. 审查只看实际改动（diff / 文件内容），不看开发者结论。
6. 门禁只允许三态：`PASS`、`FAIL`、`BLOCKED`，不得用「基本完成」代替。
7. 未验证项必须写明：未验证原因、影响范围、补验条件。
8. 数据边界只读：只读本地代码、文件与用户提供的日志；不连接数据库、缓存、远程服务。
9. 密钥、令牌、个人数据不得写入需求包、日志片段或提交信息。
10. 关键动作与验证结果必须回写 `state.md`，证据写路径而非口头结论。
11. 阻塞发生时立即记入 `state.md`，写清「卡在哪、等什么、谁能解」。
12. 发布与回退材料未齐，不得进入验收。
13. 执行 harness 必须显式调用技能入口，并在 `state.md` 记录调用来源（技能名、时间、执行者）。
14. 建仓、推送、发布等外部不可逆动作前，必须确认「项目名、目标仓库名、可见性」三项，写入 `state.md` 后才可执行；确认缺失即 `BLOCKED`。
15. UI 需求必须有冻结参考（路径 + sha1）与可重放采集命令；没有视觉证据不得进审查，`computer-use` 不得用于回归与多轮比对。
16. 动手前（改代码、改文档、发布前）必须先跑 `node harness/scripts/selfcheck.mjs`；退出码非 0 表示有阻断项，先修再动，不得带着阻断项开工。
17. 用户只提出需求时，非只读需求**自动进入需求包流程**，不等用户额外输入 `/harness` 或 `ai-workflow` 触发词；已读 `AGENTS.md` 的项目默认处于工作流内。
18. 命中某个技能后，**先读它的 SKILL.md 正文再动手**：跑 `node harness/engine/harness.mjs skill <名字>` 拿「读这个文件」的路径，读完才动手。**未读不得输出该技能的内容，也不得凭记忆复述它**。正文超长的，按该技能自己的「按需再读」表只读需要的分册，不整包吞。
19. 功能类需求（有界面、流程、入口或交互）开工前必须：① 跑 `node harness/engine/harness.mjs domain <关键词>` 查域规则；② 在需求包里写满**功能设计卡**六问（用户旅程位置 / 行业基线 / 我们的现状与差距 / 决策点与后果 / 不做什么 / 交付形态）。域规则未收录时，必须先做同行对标，并把带证据锚的行业基线沉淀到 `harness/domains/<域>.md`。缺任一项 G1 FAIL。
