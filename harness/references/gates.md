# 阶段门禁

## 1. 四道门禁

```text
G1 立项门禁（需求 + 方案，人确认）
   → G2 开发完成门禁
   → G3 验证门禁（测试 + 审查）
   → G4 发布门禁（发布/回退材料 + 人验收）
```

## 2. 三态定义

| 状态 | 含义 | 后续动作 |
|---|---|---|
| `PASS` | 全部检查项有结论且通过 | 进入下一阶段 |
| `FAIL` | 存在可修复的未通过项 | 回到对应阶段修复后重跑 |
| `BLOCKED` | 缺条件无法判定 | 记录缺什么、等谁、何时重跑 |

禁止第四种状态。禁止用「差不多」「基本可用」代替。

## 2.1 机判规则（优先于人工判断）

1. 判定顺序：先查 `state.md` 里该门禁的确认记录字段是否齐全，再查内容；字段缺失不做内容判断，直接 `FAIL`。
2. agent 只能产出 `FAIL` / `BLOCKED` / `待确认`；`PASS` 必须绑定人的确认原文，agent 自判 `PASS` 无效，按 `FAIL` 处理。
3. 每次 `gate` 只在 `state.md` 追加一行记录，不得覆盖历史。
4. 确认记录格式固定：`G<n>: <结论> | 确认人: <姓名> | 时间: YYYY-MM-DD HH:mm | 确认原文: "<原话>"`。
5. 结论与证据不一致（文档写 PASS、证据缺失）时，以证据为准，判 `FAIL`。

## 3. G1 立项门禁

| 检查项 | 通过标准 |
|---|---|
| 需求句式 | 全部写成「当…时，系统应…」 |
| 验收点 | 每条需求至少 1 个 AC，且可判定 |
| 代码证据 | ≥1 条 `path:line` / `path:line-range`，来自实际读取 |
| 边界反例 | 空、重复、无权限、超时至少覆盖 2 类 |
| 澄清清单 | 触发与时序、数据来源与精度、隐私与授权、离线与失败、存储与留存、谁可见，六类均有答复或「不适用：理由」 |
| 不做项 | 明确列出 |
| 同行对标 | 每条 `R-xx` 至少一行对标；来源为 URL 或本地证据文件，全表 ≥2 个不同来源；取舍为采纳/改造/不采纳/差异化之一 |
| 覆盖矩阵 | 有几种情况（文档里写 `覆盖维度：维度=取值; …`）与矩阵一一对应（缺值/多出未声明值均 FAIL）；每行有取值范围、已登记验收点、可追溯对标基线 |
| 方案 | 有取舍说明、影响面清单、回退思路 |
| 人确认 | 需求与方案各有一行 `G1: PASS | 确认人 | 时间 | 确认原文`，字段齐全 |

任一项缺失 → `FAIL`，不得进入开发。没有 `G1: PASS` 这行确认记录，禁止写第一行业务代码。

## 4. G2 开发完成门禁

| 检查项 | 通过标准 |
|---|---|
| 改动清单 | 与 diff 一致，无未说明改动 |
| 范围 | 无需求外改动 |
| 自测 | 命令与结果成对记录 |
| 场景声明 | 「环境」段必须写清场景（登录态/是否注入 token/参数）、入口与参数、数据准备；缺任一项 FAIL |
| 证据链 | 每个 AC 与覆盖值的 `PASS` 必须附真实证据路径（存在且非空）；`FAIL`/`BLOCKED` 必须写原因，否则 FAIL |
| 通道可用 | 需求声明的验证通道须经 `probe` 判定可用；声明了却不可用（无 playwright/无系统浏览器/无 wechatide CLI）即 FAIL |
| 未覆盖项 | 有原因与后续计划 |
| 调试残留 | 无临时日志、无硬编码密钥、无禁用代码 |

## 5. G3 验证门禁

| 检查项 | 通过标准 |
|---|---|
| 验收点覆盖 | 每个 AC 有 PASS/FAIL/BLOCKED，且 PASS 附真实证据、FAIL/BLOCKED 附原因 |
| 覆盖值覆盖 | 每个声明取值都有结论；缺任一值即最多 BLOCKED |
| 边界与异常 | 已执行并记录 |
| 回归 | 受影响功能已验证 |
| 审查问题 | 红灯清零；建议项有处理结论 |
| 独立性 | 测试与审查未读取开发自述；审查输入写明 diff 范围（命令或文件列表），否则不可信 |
| 视觉证据 | UI 需求：V 门禁 `PASS`，参考与截图路径齐全；非 UI：`state.md` 记「不适用」 |
| 未验证项 | 写明原因、影响、补验条件 |

存在 BLOCKED 时整体最多 `BLOCKED`。

## 5.1 视觉子门禁（V，UI 需求必过）

| 检查项 | 通过标准 |
|---|---|
| 参考冻结 | `visual/ref/` 有文件，且记录了 sha1、来源、冻结确认 |
| 采集可重放 | `05-visual.md` 有可执行命令，不是手工截图 |
| 截图矩阵 | 张数必须等于 `pages × states × viewports`；命名 `<page>-<state>-<w>x<h>.png`；缺一张或命名不符即 FAIL |
| 覆盖取值截图 | 需求声明的每个覆盖取值至少一张截图（可加 `<取值>-` 前缀）；缺任一取值即 FAIL |
| 状态配置覆盖 | 声明了状态维度（游客/已登录/空/加载/错误…）时，必须出现在 config 的 `pages[].states` 里，否则 FAIL |
| 内容校验 | 页面声明 `expect` 时须有 DOM 快照且含全部期望项（class/text/count）；空态例外须声明，无可见正文按疑似空页 FAIL；`expectFrom` 须已锁定且指纹一致 |
| 状态覆盖 | 默认/空/加载/错误/无权限中相关项逐项有图 |
| 比对结论 | 七个维度逐项 PASS/FAIL/BLOCKED，附参考图与实现图路径 |
| 控制台 | 无报错、无失败请求，日志路径已记录 |
| 人确认 | `V: PASS | 参考 | 视口 | 状态 | 截图 | 确认人 | 时间 | 确认原文` 字段齐全 |

缺任一 → `FAIL`。连续 3 轮不收敛 → `BLOCKED`，回需求或设计。

## 6. G4 发布门禁

| 检查项 | 通过标准 |
|---|---|
| 发布步骤 | 第二个人可照做 |
| 回退步骤 | 有触发条件与执行步骤 |
| 影响面 | 已列受影响模块与用户 |
| 监控 | 发布后看什么、看多久、异常阈值 |
| 验收 | 人确认签收 |

## 7. 简化路径

| 档 | 适用 | 简化 |
|---|---|---|
| S | 单文件、单点、无接口变更 | G1 合并为一次确认；G2 与 G3 合并为「改动 + 自测 + 一次审查」；G4 仅需回退一句 |
| M | 2–5 文件 | 全部门禁，文档可合并，验收点必须单列 |
| L | 跨模块/接口/数据变更 | 全部门禁 + 影响面清单 + 回退演练 |

简化只减少文档数量，不豁免 must 规则与三态结论。

## 8. 输出模板

```text
门禁：G3 验证门禁
需求：REQ-20261119-01
结论：FAIL
通过项：AC-01、AC-02、回归
未通过项：AC-03 取消收藏后列表未更新（复现步骤见 02-test.md §3）
阻塞项：无
下一步：修复后重跑 G3
证据：02-test.md、03-review.md、logs/req-01-test.txt
```

## 9. 记录位置

- 门禁结论写进 `state.md` 的「门禁记录」；
- 详细证据写进对应阶段文档；
- 失败与受阻必须同时写「解除条件」，否则下次无法续接。

## 10. 硬门禁细则（原 SKILL.md 正文，改需求或改流程前必读）

从 `SKILL.md` 挪到这里：细则只在动流程、改需求、判不判得过的时候才需要，平时不用背。

### 10.1 单入口与常驻规则

- 只有 `/harness` 或 `harness <begin|init|gate|handoff>` 进入本流程；自然语言需求先问一句「要不要走任务单」，得到明确同意才 `init`。
- 未 `init` 就改业务代码 = 违规，后续门禁一律 `FAIL`。
- `init` 时检查工程根有无 `AGENTS.md`；没有则复制 `templates/AGENTS.md`。常驻规则每轮注入，技能按需加载，不能靠技能自己保证生效。

### 10.2 门禁记录（`state.md`）

```text
G1: PASS | 确认人: <姓名> | 时间: YYYY-MM-DD HH:mm | 确认原文: "<用户原话>"
```

- 字段缺失、为空、仍为 `<TBD>` → `FAIL`。
- agent 只能写 `FAIL` / `BLOCKED` / `待确认`；`PASS` 必须绑定用户原话，**agent 不得自判**。

### 10.3 需求必须有证据锚

`00-requirement.md` 缺任一项即 G1 `FAIL`：

- ≥1 条现有代码定位（`path:line`，来自实际读取）；
- ≥2 类边界反例（空、重复、无权限、超时等）；
- 澄清六类齐全（触发与时序 / 数据来源与精度 / 隐私与授权 / 离线与失败 / 存储与留存 / 谁可见）。

### 10.4 续接只认文件

换对话、换工具、换 agent：先跑 `begin`（直出当前活跃包与下一步）→ 读 `harness/NEXT.md`（现场、下一步、坑）→ 读 `requirements/REQ-xxx/state.md` 与该单的 `00-requirement.md`。`harness/HANDOFF.md` 由引擎自动刷新，过期会被自检拦住，只作辅助。凭聊天记忆续接 = 违规。

### 10.5 UI 需求必须有视觉证据

- 冻结参考（路径 + sha1）+ 可重放采集命令，缺任一 `BLOCKED`。
- V 门禁行：`V: PASS | 参考 | 视口 | 状态 | 截图 | 确认人 | 时间 | 确认原文`。
- 截图张数 = `pages × states × viewports`，命名 `<page>-<state>-<w>x<h>.png`；缺一张即 `FAIL`。
- 声明了覆盖取值时，每个取值至少一张，缺一即 `FAIL`。
- 页面声明的 `expect` 必须有 DOM 快照且包含全部期望项；空态未在 `emptyAllowed` 声明照样 `FAIL`。
- computer-use 只做兜底，禁止用于回归与多轮比对。
- 连续 3 轮不收敛 → `BLOCKED`，回需求或设计。

### 10.6 每条需求先对标

- 一句话需求拆成 `R-01`…，每条写「当…时，系统应…，以便…」并配可判定 `AC-xx`。
- 每条至少一行对标：对象、来源、对方做法、我们的取舍、理由；全表 ≥2 个来源，必须是 URL 或本地证据文件。
- 查不到就写「未找到：检索范围与关键词」并转 `BLOCKED`，禁止用模型记忆充数。

### 10.7 验证沙箱当轮回收

- 沙箱建在 `os.tmpdir()`，命名 `harness-sandbox-<用途>-<时间戳>`；结束当轮跑 `clean --apply`。
- `harness/requirements/REQ-xxx/` 是交付证据，任何清理都不得删。

### 10.8 覆盖取值：声明多少做多少

- 需求分析时先写清有几种情况，格式 `覆盖维度：维度=取值1,取值2`；≥2 个取值即为多值需求，必须有覆盖矩阵。
- 矩阵与声明一一对应：缺值、多值、某值缺验收点或对标基线 → `FAIL`。
- 拿不准就反问用户，不得自行缩减，也不得默认只做第一个。
- 收尾逐值写「已完成 / 未完成 + 原因」，禁止用整体百分比掩盖。

候选维度（用于反问，不是固定清单）：端、角色/权限、状态（默认/空/加载/错误/无权限）、语言、时区、环境、数据规模、支付渠道、设备能力、浏览器版本、可访问性、弱网、账号类型、租户、币种。

### 10.9 证据链：没有产物就不算验证过

- `PASS` 必须带真实证据路径，文件存在且非空；空文件、占位符 → `FAIL`。
- `FAIL` / `BLOCKED` 必须同行写 `原因：…`。
- 每个 AC、每个取值各自留行，一条证据不能覆盖多个值。
- `02-test.md` 必须写清场景、入口与参数、数据准备（登录态、是否注入 token 等）；只测「注入了 token 的状态」不得称实测通过。
- 工具不可用 → `BLOCKED` 写清缺什么，禁止降级成「口头通过」。

### 10.10 通道探测

- 需求写 `验证通道：浏览器 / 小程序 / 桌面`；UI 或小程序需求没写就先问。
- 开工跑 `probe`（`begin` 已包含）；不可用 → `BLOCKED`。
- G2/G3 会再探测：声明了但本机不可用 → `FAIL`，「换台机器跑过了」不算。
- 证据必须是该通道的真实产物；图片会校验文件头，改名文本、空文件、旧截图一律 `FAIL`。

### 10.11 同一失败 3 次就停

- 同一检查项连续 3 次 `FAIL` 会打印「熔断」，**禁止原样重跑**。
- 三选一：换清单、换采集方式、回需求改范围；都不行记 `BLOCKED` 并写解除条件。
- 禁止用业务规则解释掉缺失（「本来就不该显示」＝把缺陷藏起来）。
