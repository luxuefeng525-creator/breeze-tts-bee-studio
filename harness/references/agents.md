# 三角色契约（开发 / 测试 / 审查）

## 1. 隔离原则

三个角色必须是三个独立上下文，彼此不共享过程推理：

| 角色 | 输入 | 禁止输入 |
|---|---|---|
| 开发 | `00`、`01`、工程规则、目标代码 | 测试与审查的中间结论 |
| 测试 | `00` 的验收点、可运行产物 | 开发自述、设计取舍理由 |
| 审查 | 实际 diff、`00`、受影响文件全文 | 开发自述、测试通过结论 |

违反隔离时，结论标记为「不可信」，需重做该角色。

## 2. 开发 Agent

### 输入

- 需求条目与验收点；
- 方案文档（含取舍与影响面）；
- 工程规则与目标文件。

### 输出契约

```text
改动清单：path:line-range — 一句话说明
实现说明：≤5 行，只讲怎么实现，不讲体会
自测记录：命令 + 结果
未覆盖项：设计里未实现的部分与原因
```

### 禁止

- 自行扩大范围（顺手重构、顺手加功能）；
- 修改需求包里的需求与验收点；
- 把「应该能跑」写成自测通过。

## 3. 测试 Agent

### 输入

- `00-requirement.md` 的全部验收点；
- 可运行的代码与启动方式。

### 检查顺序

1. 正常路径：每条验收点至少一次通过；
2. 边界：空数据、重复操作、上限、并发；
3. 异常：无权限、超时、依赖失败、取消；
4. 回归：原有相关功能是否被破坏。

### 输出契约

```text
验收点：AC-xx — PASS / FAIL / BLOCKED
复现步骤：编号步骤（FAIL 必填）
实际结果：与预期的差异
证据：命令输出路径、日志片段路径
未验证项：原因 + 补验条件
```

### 禁止

- 只看代码判断「应该没问题」；
- 跳过边界与异常；
- 用开发提供的测试结论代替执行。

## 4. 审查 Agent

### 输入

- 实际 diff（不是开发者口述）；
- 需求条目与验收点；
- 受影响文件全文。

### 检查清单

| 维度 | 检查点 |
|---|---|
| 需求一致 | diff 是否只做需求要求的事；有无漏做 |
| 权限 | 谁能触发；越权路径是否被拦 |
| 异常 | 空值、失败、取消、重试是否有处理 |
| 数据 | 读写边界、事务、重复写入 |
| 影响面 | 调用方、共享状态、配置与开关 |
| 可维护 | 命名、重复、死代码、调试残留 |
| 安全 | 密钥、注入、日志泄露 |

### 输出契约

```text
问题：严重度（阻断/建议）+ path:line + 证据 + 改法
遗留：接受理由（谁接受、何时复审）
结论：可发布 / 需修改 / 需人工决策
```

### 禁止

- 沿用开发假设（例如「这里不会并发」）；
- 只看新增代码不看调用方；
- 把风格偏好标为阻断问题。

## 5. 冲突处理

当三角色结论冲突：

1. 以需求验收点为准；
2. 验收点本身有歧义 → 回需求阶段补充，不在开发阶段吵；
3. 涉及安全与只读边界 → 直接升级给人。

## 6. 角色复用现有技能

| 角色 | 可用技能 |
|---|---|
| 开发 | `surgical-patch`、`lean-build`、`safe-refactor`、`finesse-ui` |
| 测试 | `diagnose`、`test-driven-development` |
| 审查 | `cavecrew-reviewer`、`code-review`、`verify-and-stop` |

技能只是执行方法，契约以上述输入输出为准。
