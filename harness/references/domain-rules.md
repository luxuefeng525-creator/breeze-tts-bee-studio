# 域规则机制（行业基线怎么存、怎么查、怎么沉淀）

## 1. 是什么

**域文件 = 一个角色/领域的行业基线库**，回答「这类功能，同行都做了什么、我们缺什么、哪些取舍已经定了」。

它与长期记忆（`harness/memory/`）**刻意分开**：

| | 域文件 `harness/domains/` | 长期记忆 `harness/memory/` |
|---|---|---|
| 内容 | 跨项目成立的**领域知识**（行业基线、已定取舍） | 一次性**项目经验**（踩过的坑、口径、约定） |
| 生命周期 | 长期，只增不删 | 定期复审，过期打 `[stale]` |
| 落点 | 一个域一份文件 | 正式记忆 + 候选池两个文件 |
| 谁写 | 人确认后写 | 自动写候选池，人批后晋升 |

**同一条知识不许在两处各写一份** —— 两份互相矛盾的真相源比没有更糟。

## 2. 怎么查

```bash
node harness/engine/harness.mjs domain <关键词>      # 如 骑手 / 客服 / 商家
node harness/engine/harness.mjs domain                # 不带关键词：列出已收录的域
```

- 检索**只限 `harness/domains/` 目录内**，不全仓扫
- 命中 → 输出该域全文 + 「基线 N 条 · 差距 M 条 · 取舍 K 条」
- 未命中 → 回「未收录该域」+ 已收录清单 + **下一步三步**（先对标 → 带证据锚 → 沉淀成文件），退出码 0（不是错误）

## 3. 文件结构（四块，固定）

```markdown
# 域：<域名>

## 行业基线（同行都有什么）
| 能力 | 行业做法 | 证据锚 |
|---|---|---|
| <能力> | <别人实际做到了什么> | <URL 带章节> 或 <文件:行号> |

## 我们的现状与差距
| 能力 | 现状 | 差距 |
|---|---|---|
| <能力> | <我们实际怎么做> | <缺什么> |

## 已定取舍
| 决策 | 取舍 | 理由 | 日期 |
|---|---|---|---|
| <决策> | <选了哪个> | <为什么> | <YYYY-MM-DD> |

## 变更历史
| 日期 | 变更 | 原因 |
```

## 4. 硬约束

0. **工程内 `harness/references/` 与包内 `build/v4-staging/skills/harness/references/` 必须一致** —— 引擎读的是**工程内**那份。不一致则机制在宿主里形同虚设（改动包内不生效）。改完包内记得跑 `bootstrap.mjs --apply` 同步；`selfcheck.mjs` 的「版本一致性」组会检出分叉。

1. **一条基线一个证据锚** —— 可公开引用的 URL，或内部可观测事实的 `文件:行号`。**没有证据锚的不写进文件**，只在功能设计卡里标「待核实」。
   - URL 的 `#` 后面写**页面内能搜到的标题片段**（中文页面通常没有 HTML id 锚点，所以不是严格锚点）。判定标准：把片段复制到页面里搜，能搜到即有效。
   - **证据分三层，混写会让人分不清哪条可信**：
     | 层 | 判据 | 收在哪 |
     |---|---|---|
     | 一手来源 | 厂商官方技术博客 / 官方开放平台文档 / 官方帮助中心 | 「行业基线」 |
     | 厂商自述 | 行业服务商自己写的公开产品能力说明（真实产品，但厂商自述） | 「行业基线」，并标注「厂商自述」 |
     | 参考信号 | 媒体报道 / 下载站 / 转载 | 「参考信号」，**不得单独作为基线依据** |
   - 优先一手来源。转载站只能做补充；只有转载站支撑的说法，**必须**归入「参考信号」并写明「待补一手来源」。
2. **写「他们做到了什么」，不写「竞品叫什么」** —— 「美团」不是基线，「新订单语音播报 + 一键唤起高德导航并显示剩余距离」才是。
3. **一域一文件** —— 不按项目拆、不按端拆。
4. **已定取舍追加不改写** —— 推翻旧决定时追加新行并写明推翻理由，旧行保留（防「谁改的、为什么改」失忆）。
5. **改域文件要经人确认** —— 同记忆层的晋升原则。
6. **项目特定的差距写卡，不写域文件** —— 域文件只记跨项目成立的结论。

## 5. 与功能设计卡的关系

```text
开发某域的功能
  ↓ 查 domain 命令
命中域 → 直接用基线与已定取舍，跳过对标
未命中 → 先做同行对标（feature-design §3）→ 沉淀成域文件 → 再往下走
  ↓
在功能设计卡里写：这个功能的行业基线（引用域文件哪几条）+ 我们的差距 + 决策点与后果
```

**域文件是「这个领域有什么」，功能设计卡是「这个功能怎么定」。** 两者互补，不重复。
