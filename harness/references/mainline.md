# 主线：一个需求从想法到长期沉淀，走哪十步

> 这份文件回答一个问题：**接到一个非只读需求，Agent 该按什么顺序动手，每一步谁做、谁验、产物落哪、失败退回哪。**
>
> 为什么单独成文：45 个技能各自都好用，但**没有一张地图**。
> 现实结果是——要么凭记忆挑技能（换个会话或换个工具就忘），要么把 45 个都读一遍（上下文爆）。
> 这份文件就是那张地图：**先认位置，再按图走**。
>
> 阅读方式：先看 §1 定位自己在哪一步，再看 §2 的十步动作表。别通读。
>
> **路径口径**：本文件在 `skills/harness/references/` 下。文中「同目录 xxx.md」指本目录；
> 「包根 references/xxx.md」指技能包根目录（`references/`）下的文件。

---

## 1. 五个位置（先定位，再动手）

一个需求在推进过程中只处于这五个位置之一。**认错位置 = 全程做错**。

| 位置 | 你现在有的是什么 | 对应步 | 标志动作 |
|---|---|---|---|
| ① 想法模糊 | 一句话需求，边界不清 | 步 1–2 | 对标 + 拆分 |
| ② 方案待定 | 要做什么已清楚，怎么拆、谁做未定 | 步 3–4 | 分工 + 写需求文档 |
| ③ 在实现 | 代码在写 | 步 5–6 | 实现 + 验证 |
| ④ 待验收 | 写完了，没人验 | 步 7–8 | 测试 + 返工 |
| ⑤ 已交付 | 用户能用 | 步 9–10 | 目录 + 长期记忆 |

**怎么判断自己在哪**：问一句「这件事有没有一份写下来、别人不看聊天记录也能执行的文档？」
有 → ③ 或 ④；没有 → ① 或 ②。

## 2. 十步主线

每步给七样：**做什么 · 谁做 · 谁验 · 产物落哪 · 失败退回哪 · 自检 · 清理**。

**开工先读索引**：先看 `harness/skills-index.md`，用需求关键词取最相关技能；不确定时跑 `node harness/scripts/route.mjs "<需求>"`；命中后读 SKILL.md 正文再动手，未读不得输出该技能内容。

### 步 1 · 对标（先看别人怎么做，再决定从哪开始）— 位置 ①

| | |
|---|---|
| **做** | 用 `research` 技能调研：来源分级 A/B/C/D，**只用 A/B 定结论**，每条判断挂可点的原始链接。UI 类需求先出对标表；技能进化类需求先跑 `node scripts/skill-evolve.mjs --query "<关键词>"` 拿候选 |
| **谁做** | 主 Agent，或并行只读调研代理 |
| **谁验** | 来源等级够不够（B 级以下要回溯上游）；对标点是否覆盖需求的关键取舍维度 |
| **落哪** | 写进需求包 `00-requirement.md` 的「需求分析与同行对标」段 |
| **失败退回** | 找不到 A/B 级来源 → 回需求澄清，不凭印象写结论 |
| **自检** | 五维均有结论或「不适用 + 理由」；每条 R-xx 有对标行；至少 2 个独立来源；技能候选能被 `memory.mjs ready` 解析 |
| **清理** | 删除抓取临时文件、截图草稿、重复摘要；只留对标台账与最终结论 |

对标之后必须定三件事：**做哪个**（四列表：用户现状 / 同行解法 / 我方目标 / 优先级）、**不做什么**（写进需求「不做项」）、**最像哪个**（找最接近的现成物当起点）。

**五维对标清单**（逐维写结论，缺维写「不适用 + 理由」）：

| 维度 | 要采集什么 | 落点 |
|---|---|---|
| 同类同行 | 产品形态、入口、默认值、失败处理 | 需求「对标表」的他们的做法与取舍 |
| 功能需求 | 对方功能清单与边界 | 需求条目与「不做项」 |
| UI 设计 | 布局、状态、文案、动效克制程度 | 功能设计卡「行业基线」 |
| 数据库 | 对象、关系、状态字段、索引、迁移 | `01-design.md` 数据段与拆解表 |
| 技术选型 | 语言、框架、依赖、构建、许可证 | `01-design.md` 方案对比 |

细则：`同目录 benchmark.md`（五步法 + 证据等级）。

### 步 2 · 拆分（把需求切成不打架的垂直切片）— 位置 ①

| | |
|---|---|
| **做** | 用 `to-tickets` 把需求拆成垂直切片，每张工单声明前置工单；跨模块先 `node scripts/decompose.mjs --dir <repo>` 看依赖结构 |
| **谁做** | 主 Agent 拆 |
| **谁验** | 拆完自问：**工单之间有没有共享文件？有就合并或串行**（并行写同一文件必冲突） |
| **落哪** | `harness/requirements/<REQ>/` 的工单清单，或工单系统 |
| **失败退回** | 拆完发现切片之间互相依赖 → 回到步 1 重定范围 |
| **自检** | 拆解表每列填满；同一文件只归一个切片；依赖无环；每个切片能单独验收 |
| **清理** | 删除被否决的切片草稿、空目录、重复的目录草图 |

**拆分铁律**：HUB（共享契约、公共类型、入口文件）先串行建；LEAF（互不重叠的文件）才并行。

**拆解表（步 2 的产物，不许只写一句「拆成切片」）**：

| 切片 | 目录结构 | 文件归属 | 路由 / 入口 | 函数 / 模块 | 数据表 / 字段 | 验收方式 | 清理项 |
|---|---|---|---|---|---|---|---|
| 切片 A | 新增或修改的目录 | 每个文件只归一个切片 | 命令或路由 | 函数或导出名 | 表与字段；无则写不适用 | 命令或用例 | 本切片临时文件 |

无数据库写「不适用：无持久化」；有数据库必须写可逆性与回退。空列 = 拆解未完成。

### 步 3 · 分工（谁能写、谁能读、谁能验）— 位置 ②

| | |
|---|---|
| **做** | 用 `agent-dispatch` 派工：`node scripts/agent.mjs plan "<任务>" --save`，需要结构化派工单时用 `contract` |
| **谁做** | 主 Agent 派 |
| **谁验** | 派工单是否有明确范围、验收标准、禁止项；写代理是否唯一 |
| **落哪** | 派工单与接力卡；只读代理的结论只回流结论，不回流过程 |
| **失败退回** | 两个写代理碰同一文件 → 收回并改为串行 |
| **自检** | 写代理文件清单互斥；每个派工单有范围、验收标准、禁止项；只读代理不产出代码 |
| **清理** | 撤销未执行的派工单与临时分支名；不留占位工单 |

**分工铁律**：只读代理 ≠ 写代理；侦察、实现、审查三段式。派几个看档位：L0 不派、L1 最多 1 个只读审查、L2 三段式。

细则：`skills/agent-dispatch/SKILL.md`、`包根 references/parallel.md`、`同目录 agents.md`（开发 / 测试 / 审查三份契约）。

### 步 4 · 需求文档（定边界与验收）— 位置 ②

| | |
|---|---|
| **做** | 用 `to-spec` 从用户视角写「问题定义 / 方案 / 验收标准 / 边界 / 影响面 / 对标结论」；先画 seam（在哪个 public 边界上测），新 seam 越少越好 |
| **谁做** | 主 Agent 起草 → 用户确认边界 |
| **谁验** | 用户确认「边界和验收标准对」；`harness` 门禁 G1 机判：验收点有结论、`path:line` 证据存在、边界至少 2 类、六类澄清齐全、每条需求有对标、覆盖维度与矩阵一致、功能设计卡六问齐全 |
| **落哪** | `harness/requirements/REQ-YYYYMMDD-NN/` 的 `00-requirement.md` 与 `01-design.md` |
| **失败退回** | G1 红灯 → 补需求或设计后重跑，**禁止带红灯写代码** |
| **自检** | `node harness/engine/harness.mjs gate REQ-xxx --stage G1` 退出码 0；无尖括号占位符；证据路径真实存在 |
| **清理** | 删除模板骨架与未使用章节；`[TBD]` 清零或写明未决方；不留重复段落 |

细则：`同目录 requirement-package.md`（目录布局 + 文件职责 + 生命周期）。

### 步 5 · 实现（一次只改一个模块）— 位置 ③

| | |
|---|---|
| **做** | 按工单顺序做；**先写失败测试再实现**（红→绿）。每步落 `node scripts/checkpoint.mjs`，超时长任务用 `resume` 续跑 |
| **谁做** | 写代理（单写者，别多头写同一处） |
| **谁验** | 红→绿的过程本身就是验证；改动只碰测试覆盖到的地方 |
| **落哪** | 代码 + 需求包内 `state.md` 的进度 |
| **失败退回** | 实现中发现需求有歧义 → 停手回步 4 补需求，不在代码里猜 |
| **自检** | 红→绿；受影响测试通过；语法与类型检查通过；无调试残留 |
| **清理** | 删调试打印、临时脚本、废弃分支、注释掉的旧实现、未使用依赖与空文件 |

**只改源头**：技能包改 `build/v4-staging/`，改完立刻 `node scripts/bootstrap.mjs --apply --project <工程根>`；`harness/` 与各宿主是产物。

细则：`包根 references/long-tasks.md`（断点续跑）。

### 步 6 · 验证（自己先过，别让用户当调试器）— 位置 ③

| | |
|---|---|
| **做** | 确定性检查：类型 / 语法 / 受影响单测 / `node harness/scripts/selfcheck.mjs`；技能包改动再跑 `node scripts/verify-fresh.mjs`（全新工程验收）；**阻断数必须是 0** |
| **谁做** | 主 Agent |
| **谁验** | 机检。没有命令输出 = 未完成；`PASS` 必须附真实证据路径 |
| **落哪** | 终端输出 + `02-test.md` 的自测段 |
| **失败退回** | 阻断 ≠ 0 → 回步 5 修，不带红灯进测试 |
| **自检** | `node harness/scripts/selfcheck.mjs` 阻断 0；技能包改动再跑 `verify-fresh.mjs`；证据文件非空 |
| **清理** | 删除验证沙箱、截图草稿、临时日志；保留证据文件 |

⚠️ 门禁文档里的尖括号会触发占位符判据（`--root <工程根>` 这类写法会让整行被过滤），写文档时避开。

### 步 7 · 测试（独立的人来验）— 位置 ④

| | |
|---|---|
| **做** | 独立测试代理按 `00-requirement.md` 的验收点逐条跑：正常路径 → 边界（空 / 重复 / 上限 / 并发）→ 异常（无权限 / 超时 / 依赖失败 / 取消）→ 回归；跑 G2 与 G3 |
| **谁做** | 测试代理（不参与实现，不修代码） |
| **谁验** | 每条 AC 有 PASS / FAIL / BLOCK / 待确认结论 + 证据路径；声明的覆盖取值逐值有证据 |
| **落哪** | `harness/requirements/<REQ>/02-test.md` 与 `evidence/` |
| **失败退回** | 任一 AC FAIL → 进步 8 返工，**不得自己顺手改** |
| **自检** | 每条 AC 有 PASS/FAIL/BLOCKED 与证据；覆盖值逐项有结论；测试场景写明入口与数据准备 |
| **清理** | 删除失败复现的临时数据与沙箱；保留复现步骤与证据 |

### 步 8 · 返工（修完要重验，不是修好就算）— 位置 ④

| | |
|---|---|
| **做** | 审查或测试的问题**打回给写代理**（不是验收人顺手改）→ 写代理按问题清单修 → **重新走步 6 验证与步 7 测试** |
| **谁做** | 写代理修；原验收人重验 |
| **谁验** | 同一判定标准重跑；不允许「上次失败这次跳过」 |
| **落哪** | `03-review.md` 问题清单 + `02-test.md` 返工记录 |
| **失败退回** | 同一问题连续 3 次 FAIL → 熔断，回步 4 重定需求或记 BLOCKED，禁止原样重跑 |
| **自检** | 每个问题有严重度、位置、改法、状态；阻断清零；重跑用同一判定标准 |
| **清理** | 删除废弃补丁、临时回滚分支、过期复现脚本；不删失败记录 |

**返工禁忌**：把「修好了」当「验过了」；用开发自述替代测试执行；扩大范围顺手重构。

### 步 9 · 目录（让谁都能找到、能接手）— 位置 ⑤

| | |
|---|---|
| **做** | 在技能包根目录重建索引与目录：`node scripts/build-skills-index.mjs`、`node scripts/build-catalog.mjs`、`node scripts/audit-skills.mjs`；再 `node scripts/bootstrap.mjs --apply --project <工程根>` 把索引与文档同步到工程与各宿主；工程入口同步跑 `node harness/engine/harness.mjs refresh` |
| **谁做** | 主 Agent |
| **谁验** | 索引条目数与技能审计结果一致；目录里的命令逐条能跑；索引过期由自检拦住 |
| **落哪** | 包根 `references/skills-index.md`、`catalog.json`、工程 `harness/skills-index.md` |
| **失败退回** | 索引脚本缺失或条目数不一致 → 中止，不出半份索引 |
| **自检** | `build-skills-index.mjs --check` 通过；技能审计 45/45；分发包与版本一致 |
| **清理** | 删除过期索引副本、孤儿分发包、空目录、超阈值备份；保留最近一版可回滚备份 |

**为什么单列**：目录过期比没有目录更糟——它看起来是权威的。

**收口清单（结项 / 发布必做，缺一步不算收口）**：`build-skills-index.mjs` → `audit-skills.mjs` → `release.mjs --pack`（提交后） → `bootstrap.mjs --apply --install-missing --project <工程根>`（**同步宿主**） → `selfcheck.mjs` 阻断 0。第 4 步漏了，源里的改动只留在源里，工程与 6 个宿主仍跑旧副本。

### 步 10 · 长期记忆（让下一次更快）— 位置 ⑤

| | |
|---|---|
| **做** | 教训进候选池：`node harness/scripts/memory.mjs add "<事实>" --scope <域> --source <证据路径> --cat 经验`；门禁通过会自动回流候选；开工时 `memory.mjs brief "<这次要做什么>"` 取经验 |
| **谁做** | 主 Agent |
| **谁验** | 满足晋升通道（常规 3 次复现 / 2 个作用域 / 30 天；快速 5 次 / 3 域 / 7 天；或有证据 + 人工担保）后，`promote <候选号> --confirm` 进正式记忆；`search` / `brief` 展示的正式条目自动记召回 |
| **落哪** | 候选池 `harness/memory/inbox.md` → 正式 `harness/memory/long-term.md`；交接写 `harness/NEXT.md` 手写层（`harness/HANDOFF.md` 由引擎自动刷新） |
| **失败退回** | 候选被拒（事实太短 / 无证据 / 路径不存在）→ 补证据重写，不绕过校验 |
| **自检** | `memory.mjs stats` 形状异常 0；`ready` 能列出待提炼；`search` 有召回记账；`selfcheck` READY |
| **清理** | 合并重复观察、过期候选进复审、删除验证沙箱；不改写历史失败记录 |

**自我进化链**：

```text
门禁通过 → 结论连证据自动入候选池
  → 人工提炼成可复用经验
  → 同一教训重复出现自然聚合（复现次数 +1）
  → 满足通道 → 人的确认 → promote 进正式记忆
  → 下次 brief / search 能召回并自动记账 → 少踩一次坑
```

**关键**：**自动写入 ≠ 生效**。只有人确认晋升的条目才是「生效的规则」。没确认的只是留档。

细则：`包根 references/memory-spec.md`（记忆模型 + 晋升通道 + 省 token 铁律）。

### 2.1 清理分级（A/B/C）

| 级别 | 含义 | 举例 | 动作 |
|---|---|---|---|
| **A 自动** | 无价值、可再生、无审计意义 | 空目录、临时沙箱、调试打印、模板占位、`node_modules` | 当轮删除，在 `state.md` 清理记录留一行 |
| **B 确认** | 可能复用或属于他人产物 | 示例目录、日志目录里的脚本、历史审计结果、旧包、恢复备份 | 列清单，人确认后删除或迁移 |
| **C 永不删** | 交付证据、记忆、用户资料、版本历史 | 需求包与 `evidence/`、`long-term.md`、`重要不能删除/`、`.git` | 只读，禁止自动删除 |

- 删除路径必须落在项目内；越界直接拒绝。
- B 类必须有人确认原文；C 类连整理都不做。
- 清理结果写进需求包 `state.md` 的「清理记录」段，提交说明里写一句删了什么。

## 3. 目录与文件放哪（谁都能找到、都能接手）

### 3.1 项目侧

```text
harness/
├── requirements/REQ-YYYYMMDD-NN/   一个需求一个包（见 requirement-package.md）
│   ├── 00-requirement.md   需求 + 对标 + 验收点
│   ├── 01-design.md        设计
│   ├── 02-test.md          测试与 AC 结论 + 证据路径
│   ├── 03-review.md        审查问题清单
│   ├── 04-release.md       发布与回退
│   ├── 05-visual.md        视觉证据（UI 需求必填）
│   ├── state.md            本需求的进度、阻塞、门禁记录、下一步
│   ├── evidence/           证据文件（AC 结论要指得到）
│   └── visual/             ref 冻结参考、shot 截图
├── memory/                 记忆（inbox 候选池 / long-term 正式）
├── references/             规范（rules / gates / agents / benchmark / mainline）
├── engine/ + scripts/      引擎与脚本
├── domains/                行业基线（一域一份）
├── logs/                   运行日志
├── NEXT.md                 下一步（生成层 + 手写层）
└── HANDOFF.md              自动刷新的接手快照（不是第一手现场）
```

模板文件在包内叫 `templates/requirement.md` 等，`init` 时才落成带编号的 `00-requirement.md`。

### 3.2 能力侧（技能包内）

```text
skills/<技能名>/
├── SKILL.md          触发条件 + 流程（frontmatter 的 description 是路由依据）
├── references/       细则（按需加载，别整份读）
└── scripts/          该技能的脚本
```

**硬规矩**：
- **改代码只改 `build/v4-staging/`（源）**，改完立刻 bootstrap。`harness/` 与各宿主都是产物，改产物会被静默覆盖。
- **文档要能被没见过的人看懂**：新工程里 `init` 出来的模板若缺关键字段，验收命令会直接报出来。

---

## 4. 四条贯穿全程的铁律

1. **先文档后动手** —— 任何非只读动作前，先有需求/设计/工单；没有文档就写代码 = 流程违规，即使代码能跑。
2. **先证后言** —— 没有证据的结论不进文档、不进汇报。
3. **人机边界清楚** —— 拍板在人，执行在 Agent；Agent 不替人做「要不要做」的决定，只替人做「怎么做得对」。
4. **失败留痕** —— 失败记录不删不改，它是改进依据（门禁的 FAIL→PASS 轨迹就是训练材料）。
