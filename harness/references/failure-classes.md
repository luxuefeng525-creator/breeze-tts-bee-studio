# 高频失败类与对应机制

> 这份文件回答一个问题：为什么「跑了很多轮还是漏」，以及哪些环节必须交给机器判、哪些只能靠人。
> 先把失败分类，再对每一类放一个机判点；没有机判点的，明确标成「人负责」。

## 1. 失败分类表

| # | 现象 | 根因 | 机判点 | 仍需人 |
|---|---|---|---|---|
| 1 | 只做一个端 / 一个角色 / 一种状态 | 范围没声明，做多少算多少 | G1「覆盖维度与矩阵一致」集合比对 | 确认清单本身是否想全 |
| 2 | 少了一个容器，检查还说通过 | 期望清单只扫页面函数，漏掉辅助函数拼出的组件 | V「内容校验」：`expect` + DOM 快照 | 清单必须来自全量清单评审 |
| 3 | 空数据时直接 PASS | 把「没数据」当成「没问题」 | V：空态缺项 FAIL；可见正文过短按疑似空页 | 确认哪些项是设计上确实没有 |
| 4 | 说「跑过了」但没证据 | 结论只有文字 | G2/G3 证据链：路径存在且非空、图片验文件头 | 证据是否真的对应该功能 |
| 5 | 拿旧截图 / 旧日志顶替 | 没有时效与指纹 | `expectFrom` 锁定 sha1；证据路径校验 | 定期复核 |
| 6 | 只做一半就报完成 | 汇报用整体进度掩盖缺口 | G1/G2/G3 逐值结论；handoff 逐值状态 | 验收时逐项过 |
| 7 | 工具没装，假装跑过 | 没有能力探测 | `probe` + 通道可用性 FAIL | 装工具、授权登录 |
| 8 | 换个 AI / 换台机器就接不上 | 上下文只在聊天里 | `begin` 直出活跃包 + `HANDOFF.md` 自动刷新 + 三处入口 + state.md | 自检拦截过期 HANDOFF |
| 9 | agent 自己判 PASS | PASS 没有人类原文 | 门禁机读行必须含确认人/时间/原文 | 人给确认 |
| 10 | 原型改了，清单还是旧的 | 清单与来源脱钩 | `expectFrom` 指纹不一致即 FAIL | 重评清单 |
| 11 | 每轮只修被指出的那一处 | 修个案，不修检查方法 | 把规则写进引擎，而不是写进对话 | 复盘失败类，补规则 |
| 12 | 界面「不好看」「不像」 | 审美与一致性无法机判 | 只能冻结参考 + 逐维比对 | 人验收 |
| 13 | 只测注入 token/加参数的路径，就宣布实测通过 | 测试场景与用户实际场景不一致 | G2/G3「测试场景已声明」：场景/入口参数/数据准备必填 | 按用户真实路径复现 |

## 2. 三条基本原则

1. **判断权在脚本，解释权在模型**：模型负责采集、填写、解释失败原因，不负责宣布通过。
2. **声明即承诺**：先把范围（维度/取值）、期望（组件/文案）、通道（浏览器/小程序/桌面）写下来，门禁只对「写下来的」做集合比对。
3. **一次全量，可复核**：清单一次扫全并锁定指纹；证据一次落盘并保留；不允许「上次跑过」。

## 3. 机器管不到的三件事（必须人来）

| 事项 | 为什么机器不行 | 补法 |
|---|---|---|
| 清单完整性 | 机器不知道「还应该有什么」 | 人工按原型全量评审清单，`--approve` 锁定 |
| 证据对应性 | 文件存在 ≠ 拍的是这个功能 | 证据命名带 AC/取值，验收时抽查 |
| 设计与审美 | 「像不像 / 好不好看」无客观阈值 | 冻结参考、逐维比对、人签收 |

## 4. 自查：一条需求是否真的做完了

按顺序问，任一答不上就不能报完成：

1. 范围声明了吗？端、角色、状态、语言、环境各是什么？
2. 每条需求都对标过同类与同行吗？来源能打开吗？
3. 每个 AC、每个覆盖取值都有独立结论与证据吗？
4. 证据是这次跑出来的吗？文件头/格式对吗？有没有超过时效？
5. 声明的验证通道真的可用吗？跑过吗？
6. `handoff` 里「未过」是空的吗？下一步具体到文件和命令吗？

## 5. 连续失败与「解释掉」

**连续 3 次同一个检查项 FAIL → 停手。** 引擎会打印「熔断」。原样重跑只会消耗对话轮次，必须换一个变量：

| 换什么 | 具体动作 |
|---|---|
| 换清单 | `inventory` 重新生成候选，人工重评 `expect`，`gate V --approve` 重新锁定 |
| 换采集 | 换通道（浏览器 ↔ 小程序 ↔ 桌面）、换快照方式（HTML ↔ JSON）、换视口 |
| 换范围 | 回 `00-requirement.md` 改覆盖维度，删掉不该做的项（要人确认） |
| 以上都不行 | 记 `BLOCKED`，写清缺什么、谁解、何时重跑 |

**禁止用业务规则解释掉缺失。** 下面三句话都是 red flag：

- 「按规则它本来就不该显示」
- 「数据为空所以看不到」
- 「这个条件不满足，所以不需要」

正确做法只有两条：补实现（哪怕空态也要有容器/占位），或者把该项从清单删除并由人重新 `--approve`。私自删清单 = 改考题。
